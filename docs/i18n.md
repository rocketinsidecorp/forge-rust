# Internationalization (i18n)

Forge's `forge::i18n` is Rails I18n for Rust: translations in
`config/locales`, dotted keys, `%{name}` interpolation, CLDR plural forms, a
locale per request, and localized numbers and dates. Forge-Go reads the same
files with the same results. The decisions, limits and differences from
Forge-Go are in [ADR 0037](adr/0037-internationalization.md).

## Quick start

```sh
forge new shop --locale pt-BR       # en.json and pt-BR.json; pt-BR is the default locale
cd shop
forge dev
curl -H 'Accept-Language: en' http://127.0.0.1:3000/      # "Welcome to shop"
curl -H 'Accept-Language: pt-BR' http://127.0.0.1:3000/   # "Bem-vindo ao shop"
forge i18n check                    # every locale complete?
```

`--locale` accepts `en` (the default), `es` and `pt-BR`: Forge ships the
text of the generated pages in those languages. Add any other locale by
copying a file (below).

## Translation files

```text
config/locales/en.json                  layout, welcome page, number and date formats
config/locales/pt-BR.json               the same keys in Brazilian Portuguese
config/locales/authentication.en.json   sign-in and password-reset pages (PostgreSQL)
config/locales/posts.en.json            added by `forge generate scaffold post ...`
src/adapters/http/views/locales.rs      DEFAULT_LOCALE and translator(config)
build.rs                                embeds config/locales/*.json in the binary
```

A file is `LOCALE.json` or `SCOPE.LOCALE.json`. It holds one object whose
only key is the locale, as in a Rails YAML file:

```json
{
  "en": {
    "users": {
      "welcome": "Welcome back, %{name}!",
      "intro_html": "<strong>%{name}</strong> joined %{team}",
      "inbox": {
        "zero": "No messages",
        "one": "%{count} message",
        "other": "%{count} messages"
      }
    }
  }
}
```

- Keys are dotted paths (`users.welcome`); segments use letters, digits,
  `_` and `-`.
- The files of a locale are merged. A key defined twice, in one file or
  across files, stops the application at startup, naming both files.
- Locales are `language[-Script][-REGION]`: `en`, `pt-BR`, `zh-Hant-TW`,
  `es-419`. Name files canonically: `pt-br.json` is refused with the right
  name. The available locales are the files present.
- Limits: 1 MiB per file, 512 files, 16 levels, 50,000 keys per locale.
- Converting a Rails file: `yq -o json config/locales/fr.yml > fr.json`.
- The files are embedded at build time (`build.rs` reruns when one changes);
  `cargo build` after editing them.

### Adding a locale

```sh
cp config/locales/en.json config/locales/fr.json
cp config/locales/authentication.en.json config/locales/authentication.fr.json   # PostgreSQL applications
# translate the values and rename the top-level key "en" to "fr" in both files
forge i18n check
```

## Using translations

In templates (`templates/`), through the layout every page has:

```html
<html lang="{{ layout.i18n.locale() }}">
<h1>{{ layout.i18n.t("users.welcome").with("name", user.name) }}</h1>
<p>{{ layout.i18n.t("users.intro_html").with("name", user.name).with("team", team) }}</p>
<p>{{ layout.i18n.t("users.inbox").count(unread) }}</p>
<p>{{ layout.i18n.l(created_at, "short") }} · {{ layout.i18n.l(birthday, "date.formats.long") }}</p>
<p>{{ layout.i18n.number(total) }} · {{ layout.i18n.number_with_precision(price, 2) }}</p>
```

In handlers (flash messages, titles of your own):

```rust
let i18n = site.i18n(&request);
let notice = i18n.t("posts.flash.created").text();
let message = i18n.t("throttled.sign_in").count(minutes).text();
let mut response = forge::web::html(&page);
```

`with` fills `%{name}` with any `Display` value; `count` also selects the
plural form. Dates are `forge::i18n::DateTime` values
(`DateTime::from_unix(chrono_value.timestamp())`,
`DateTime::from_system_time(SystemTime::now())`, `.with_offset(-3 * 3600,
Some("BRT"))`).

Outside a request (jobs, mailers), bind a locale yourself:

```rust
use forge::i18n::Args;

let subject = translator.translate(&user.locale, "mailers.welcome.subject", &Args::new().with("name", &user.name));
let i18n = forge::views::I18n::new(translator.clone(), &user.locale);   // for an Askama email template
```

### Escaping

- `{{ layout.i18n.t("key") }}` renders HTML: a plain key's text is
  HTML-escaped, arguments included, so it is safe in element content and
  quoted attributes. Askama does not escape it again, and `|safe` does not
  change it: a plain key never becomes markup.
- Keys ending in `_html` (or named `html`) are trusted markup from your own
  files: the text is not escaped, every argument is HTML-escaped unless
  passed with `.with_markup(name, markup)`. Never build such a key from
  request input, and never interpolate URLs from users into an `href`
  inside one. A translation such as `<a href="%{url}">...</a>` has its
  value HTML-escaped but not checked as a URL: `javascript:alert(1)` passes
  through unchanged, as in Rails. Only pass URLs your own code builds
  (`/posts/1`, a configured host); put links to user-supplied addresses in
  the template.
- `.text()` (and `Translator::translate`) returns the text as written: the
  markup of `_html` keys with escaped arguments, plain keys unescaped for
  the caller's context. A flash message is escaped when the layout renders
  it. `Translator::translate_html` escapes plain keys.

### Plural forms

Plural objects use the CLDR categories `zero`, `one`, `two`, `few`, `many`
and `other` (`other` is required). Forge picks the category with the CLDR 46
rule of the locale the text came from, for integer and decimal counts:

| Locales | Forms to write |
| ------- | -------------- |
| en, de, nl, sv, nb, fi, et, es, it, pt-PT, tr, el, hu | `one`, `other` |
| pt, pt-BR, fr (0 and 1 are `one`) | `one`, `other` |
| ru, uk, pl | `one`, `few`, `many` (and `other` for fractions) |
| cs, sk | `one`, `few`, `other` (`many` for fractions) |
| ar | `zero`, `one`, `two`, `few`, `many`, `other` |
| he | `one`, `two`, `other` |
| ja, zh, ko, vi, th, id, ms | `other` |

An explicit `zero` form is used for 0 in every language; without a count a
plural key gives its `other` form. A form the rule chooses but the file
lacks falls back to `other` (Spanish, French, Italian and Portuguese `many`
is only for whole millions). Other languages use `other` until you add a
rule in `src/adapters/http/views/locales.rs`:

```rust
use forge::i18n::{Category, Operands};

// CLDR "cy" (Welsh), from https://cldr.unicode.org/index/cldr-spec/plural-rules
fn welsh(o: Operands) -> Category {
    if o.v != 0 {
        return Category::Other;
    }
    match o.i {
        0 => Category::Zero,
        1 => Category::One,
        2 => Category::Two,
        3 => Category::Few,
        6 => Category::Many,
        _ => Category::Other,
    }
}

// Options::new().default_locale(...).plural_rule("cy", welsh)
```

`Operands` are CLDR's n (absolute value), i (integer digits) and v (number
of visible fraction digits). The rules read the count as CLDR does: `1.0` is
`other` in English but `one` in Norwegian, Turkish, Greek, Hungarian and
Spanish (`n = 1`), and Arabic works on n, so `0.0`, `1.0`, `2.0` and `103.0`
are `zero`, `one`, `two` and `few`. NaN and infinity are `other` in every
language: the lookup answers that before any rule runs, for the built-in
rules and your own alike, so a custom rule never sees them.

### Numbers and dates

`number` and `l` read Rails' keys from the locale (then its parents, the
default locale, then built-in English):

```json
{"pt-BR": {
  "number": {"format": {"separator": ",", "delimiter": ".", "precision": 2}},
  "date": {"formats": {"long": "%-d de %B de %Y"},
           "month_names": [null, "janeiro", "fevereiro", "março", "abril", "maio", "junho",
                           "julho", "agosto", "setembro", "outubro", "novembro", "dezembro"]},
  "time": {"formats": {"short": "%d/%m %H:%M"}, "am": "", "pm": ""}
}}
```

`l(value, "short")` uses `time.formats.short`; a name with a dot is a full
key. Directives: `%Y %y %m %d %e %j %H %I %M %S %p %P %A %a %B %b %z %Z %%`;
`%-d` drops the padding; `%y` is the year modulo 100 and never negative
(year -5 is `95`). `number(1234.5)` is `1.234,50` in pt-BR; integers
get no decimals unless a precision is given.

## Choosing the locale

`LocaleNegotiation` (registered first by `Site::register`) picks, in order:

1. the first path segment, with `.with_path_prefix()` (`/pt-BR/posts` is
   served by `GET /posts`; the segment must be an available locale);
2. a query parameter, with `.with_param("locale")?` (`?locale=pt-BR`);
3. the `locale` cookie (`.with_cookie(name)?` renames it);
4. `Accept-Language`, by quality (`q=0` excluded, `*` means the default);
5. the default locale: `FORGE_I18N_DEFAULT_LOCALE`, else `DEFAULT_LOCALE` in
   `src/adapters/http/views/locales.rs` (`forge new --locale`), else `en`.

A requested locale matches itself, else its parent (`pt-PT` → `pt`), else a
variant of its language (`pt` → `pt-BR`). Invalid names are ignored, so a
header, cookie or URL can never name a file. Responses that used the
request's translations (every page with the layout) carry
`Content-Language` and `Vary: Accept-Language, Cookie`; digested assets,
JSON and health probes do not, so they stay cacheable. A translated response
built without the binding can call `forge::views::set_content_language`.
`LocaleNegotiation::negotiate(&request)` only answers which locale the
request wants; it has no response to mark, so a handler whose answer depends
on it (a redirect to `/pt-BR/`, say) gets no `Vary` and no
`Content-Language` by itself. Call `set_content_language` on that response,
or add `Vary: Accept-Language, Cookie` yourself, or a shared cache can serve
one visitor's redirect to another.

To opt into the prefix and the parameter, build the layer `Site::register`
installs like this (the names are validated, so `with_param` and
`with_cookie` return a `Result`):

```rust
fn negotiation(translator: Arc<Translator>) -> Result<LocaleNegotiation, I18nError> {
    LocaleNegotiation::new(translator)
        .with_path_prefix()
        .with_param("locale")
}
```

With the path prefix, the locale segment is removed before any layer
handles the request: the router runs every layer's rewrite step
(`Middleware::rewrite`) first, and the negotiation layer strips the segment
there. Every layer, wherever it is registered, and the route table see
`/posts` for `/pt-BR/posts`; only the server's request telemetry logs the
path as sent. The segment is read from the escaped path the router matches,
so `/pt-BR%2F..%2Fadmin` has no locale segment, and it is removed once, so
`/pt-BR/en/admin` is routed as `/en/admin`.

A path-sensitive security layer (an `/admin` guard, an IP allow-list for
`/metrics`, a path-based rate limit or filter) therefore sees `/admin` for
`/pt-BR/admin` in either order: a locale prefix cannot bypass it. This is
enforced by the router, not by registration order, and tested with a guard
registered before and after the negotiation layer
(`a_locale_prefix_cannot_bypass_a_path_guard_registered_before_the_negotiation`).
A layer of your own that rewrites the path for routing should do it in
`rewrite` too, for the same reason.

Redirects you write yourself drop the prefix unless you add it: build them
with it. The sign-in return path is the exception. The layer keeps the
segment it removed, as the locale's canonical name (`/PT-br/posts` is kept as
`/pt-BR`, never the request's spelling), and `forge::views::path_prefix(&request)`
returns it. `SignInRedirect` puts it back in front of the path, so
`/pt-BR/posts?page=2` sends the visitor to
`/session/new?return_to=%2Fpt-BR%2Fposts%3Fpage%3D2` and back to the page in
their language after sign-in, in either layer order. The finished
path must still pass `return_path`: `//evil.example`, `/pt-BR//evil.example`,
backslashes and anything else that is not a path on this site are refused
with or without a prefix, and then the unprefixed path (or none) is used.

A language switcher stores the choice:

```rust
router.route(Method::POST, "/locale", move |request: Request| {
    let translator = Arc::clone(&translator);
    async move {
        let chosen = request.form_value("locale").ok().flatten().unwrap_or_default();
        match forge::views::locale_cookie(&translator, None, &chosen) {
            Ok(cookie) => {
                let mut response = forge::views::see_other("/").unwrap_or_else(|_| Response::empty(StatusCode::SEE_OTHER));
                if let Ok(value) = HeaderValue::from_str(&cookie) {
                    response.headers_mut().append(header::SET_COOKIE, value);
                }
                response
            }
            Err(_) => Response::new(StatusCode::UNPROCESSABLE_ENTITY, "unknown locale"),
        }
    }
})?;
```

The cookie is `Secure`, `HttpOnly`, `SameSite=Lax`, for a year. The route is
behind the CSRF layer like any form.

```sh
FORGE_I18N_DEFAULT_LOCALE=pt-BR forge dev
curl -si -H 'Accept-Language: fr-CA, pt;q=0.8' http://127.0.0.1:3000/ | grep -i content-language   # pt-BR
curl -si --cookie 'locale=en' http://127.0.0.1:3000/ | grep -i content-language                       # en
```

`FORGE_I18N_DEFAULT_LOCALE` must be spelled canonically (`pt-BR`, not
`pt-br`) and have its `config/locales/LOCALE.json`; otherwise the
application refuses to start.

## Missing translations

| Environment | Missing key shows | Then |
| ----------- | ----------------- | ---- |
| development, test | `translation missing: pt-BR.posts.index.title` | warning logged once |
| production | the default locale's text, else the key humanized ("Title") | warning logged once |

The locale's parents are always tried first (`pt-BR` → `pt`). Nothing
panics: an unknown key, a missing `%{name}` value (left as written) or a
`count` that is not a number are logged. Generated tests fail when a page
shows `translation missing`.

Warnings are remembered for at most 1,024 distinct problems, so keys built
from request input cannot grow memory or the log. The first problem past
that logs one `missing-translation warnings suppressed` line; later new ones
are only counted (`translator.suppressed_warnings()`).

## `forge i18n check`

```sh
forge i18n check          # human report; exit 1 when a locale lacks keys or plural forms
forge i18n check --json   # schema-versioned report for CI and agents
```

```text
config/locales: en, pt-BR; 82 keys, 64 referenced in templates and Rust code

en: complete

pt-BR: 2 missing
  posts.index.title
  posts.flash.created

unused: 1 (no literal t("KEY") or translate(locale, "KEY") found; keys built at runtime are not detected)
  users.old_banner
```

It compares every locale with the keys of all the others and with the
literal keys in `.t("KEY")` (templates and Rust) and
`translate(locale, "KEY")` / `translate_html(locale, "KEY")` (Rust; the
`tests` directory and build output excluded), checks the plural forms each
locale's rule needs, and lists keys nothing references. Keys built at
runtime are not seen; `date.*`, `time.*` and `number.*` are data and never
reported unused. It reads files only and never runs application code.

## Generators

| Command | Translations |
| ------- | ------------ |
| `forge new NAME [--locale es\|pt-BR]` | `config/locales` with the layout, welcome page and (PostgreSQL) authentication pages |
| `forge generate scaffold post ...` | `config/locales/posts.en.json`, and `posts.LOCALE.json` with the same English text when the application's default locale (`DEFAULT_LOCALE`) is another one, so production shows English, not humanized keys, until you translate it; pages use `layout.i18n.t`, flash messages `.text()`. The plural cannot be `date`, `time` or `number` (formatting scopes) |
| `forge generate authentication` | `authentication.en.json`, plus `authentication.es.json`/`pt-BR.json` when those locales exist |

### Applications created before i18n

The generators refuse an application without
`src/adapters/http/views/locales.rs`. To upgrade one by hand, compare with a
fresh `forge new` application of the same version:

1. copy `config/locales/` and `src/adapters/http/views/locales.rs` (set
   `DEFAULT_LOCALE`), and add `forge_views::build::embed_locales("config/locales")`
   to `build.rs`;
2. in `src/adapters/http/views/mod.rs`, declare `pub mod locales;`, keep the
   translator in `Site` (`Site::load(translator)`), register
   `LocaleNegotiation::new(...)` first in `Site::register`, and give `Layout`
   the field `pub i18n: I18n` (`Site::layout(request)`, `Site::i18n`,
   `Site::default_i18n`);
3. in `src/adapters/http/mod.rs` and `src/bootstrap/mod.rs`, build the
   translator with `views::locales::translator(composition.config())` and
   pass it to `site`;
4. use `{{ layout.i18n.locale() }}` and a `title` block in the layout.

Framework validation messages and the scaffold's Yes/No values are still
English: see the follow-ups in ADR 0037.
