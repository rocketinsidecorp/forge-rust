# ADR 0035: Mail

- Status: Accepted
- Date: 2026-10-20
- Refines: [ADR 0026](0026-authentication-pages-and-setup.md) (password reset links are now delivered when mail is configured)
- Ported from: Forge-Go ADR 0024 (same variables, limits, encoder output, error codes and negative tests)

## Context

Applications need to send email: password reset links today, receipts and
notifications next. Rails' Action Mailer is the reference experience (mailer
templates, previews, a test delivery list); Forge-Go ships it as the `mail`
package with the failure modes closed: messages built from untrusted input
cannot inject headers, recipients or MIME parts; production never sends
credentials or mail in clear by accident; a template error never produces a
half-rendered email. Forge-Rust generated applications had sign-in and reset
pages, but their `PasswordResetNotifier` was the fail-closed
`UndeliverablePasswordResets`, so reset links could not be delivered.

## Decision

### Crate and rings

`forge-mail` holds the `Sender` port, the message model and encoder, the SMTP,
development file and test senders, askama templates, the preview handler, the
telemetry wrapper and the password reset adapter. The `forge` facade
re-exports it as `forge::mail` under the feature `mail`, which `views` turns on
(full-stack applications get a mailer, like Rails); API applications opt in.

| Ring | Mail parts |
| --- | --- |
| application | `Sender`, `Message`, `Address`, `Attachment`, `Templates` (the port and plain data) |
| infrastructure | `SmtpSender`, `FileSender`, `Instrumented`, `PasswordResetMailer` (implements `forge_auth::PasswordResetNotifier`) |
| HTTP adapter | `PreviewHandler` (a `forge_http::Middleware`) |
| bootstrap | `from_config`, `password_reset_notifier`: the only places that read `FORGE_MAIL_*` and select a sender |

`forge-auth` does not depend on `forge-mail`; the adapter depends on both
contracts, as Forge-Go's `auth/recoverymail` does.

### Messages are data, validated at the boundary

Every sender (the test recorder included) calls the encoder before any side
effect, so there is no path from a `Message` to a transport that skips
validation. The rules are Forge-Go's, byte for byte:

- control characters (CR, LF, NUL, all of C0/C1, DEL, U+2028/2029, U+FFFD)
  and bidirectional overrides, isolates and marks are rejected in every
  header-bound string; errors name the field and rule, never the value;
- addresses are ASCII dot-atom `local@domain` with an LDH domain, at most 254
  bytes; quoted local parts, comments, route addresses and domain literals
  are rejected. The single definition lives in `forge_config::validate_mailbox`
  and also checks `FORGE_MAIL_FROM`. Non-ASCII addresses are
  `mail_address_unsupported` (no SMTPUTF8, no IDNA, never punycoded);
- non-ASCII subjects and names are RFC 2047 encoded; ASCII text containing
  `=?` is base64-encoded whole so a client cannot decode attacker-chosen
  text; headers fold below 78 columns without whitespace-only lines or
  trailing whitespace;
- extra headers come from an allow-list (`Auto-Submitted`, `In-Reply-To`,
  `List-Id`, `List-Unsubscribe`, `List-Unsubscribe-Post`, `Precedence`,
  `References`), printable ASCII only; `Bcc` exists only in the envelope;
- limits: subject 255 characters, 100 recipients, 2 MiB per body, 10
  attachments of at most 7 MiB, 10 MiB in total; file names are reduced to a
  base name and refused with control or direction-override characters;
  `multipart/*` and `message/*` attachment types are refused;
- `Date` is UTC, `Message-ID` is `<UUIDv7@sender-domain>`, bodies are
  quoted-printable UTF-8 and attachments base64 with 128-bit random
  boundaries; structure is `text/plain`, `text/html`, `multipart/alternative`,
  `multipart/related` for inline images and `multipart/mixed` for files.

The encoder is a port of the Go standard library functions Forge-Go calls
(`mime.WordEncoder`, `mime/quotedprintable`, `mime.FormatMediaType`,
`net/mail.Address.String`, `mime/multipart`), and golden tests compare its
output with Forge-Go's for the same messages byte for byte.

### SMTP: a small Forge-owned client

`SmtpSender` is a few hundred lines over Tokio, `rustls` and `tokio-rustls` that
speak only what submission needs: greeting, EHLO (HELO fallback), STARTTLS,
AUTH PLAIN or LOGIN, MAIL, RCPT, DATA with dot-stuffing, QUIT.

- `smtp://` requires STARTTLS; `smtps://` uses implicit TLS. A server that
  does not advertise STARTTLS is refused (`mail_tls_required`) before AUTH,
  MAIL or DATA, so a stripped advertisement cannot downgrade the connection.
- Certificates and names are always verified, TLS 1.2 or 1.3, with the
  Mozilla roots (`webpki-roots`) plus `FORGE_MAIL_TLS_CA_FILE`. There is no
  setting to skip verification.
- Bytes the server sends after `220` to STARTTLS and before the handshake
  are refused (`mail_tls_failed`), closing the STARTTLS command-injection
  class (CVE-2011-0411).
- `FORGE_MAIL_ALLOW_PLAINTEXT` covers the **message**, never the
  **password**: AUTH without TLS goes only to a loopback host (`localhost`,
  127.0.0.0/8, `::1`); towards any other host the send fails with
  `mail_auth_failed` before the password leaves the process, and production
  configuration refuses the flag together with credentials for a remote host.
  When STARTTLS is offered it is still used, and a TLS failure never falls back.
- Every reply line (2048 bytes) and reply (128 lines) is bounded; the whole
  delivery runs under `FORGE_MAIL_TIMEOUT` (default 30 s, at most 10 min) and
  the TCP connect under 10 s. Dropping the future closes the connection; no
  task is spawned.
- One connection per message, no pooling. A refused recipient aborts before
  DATA. Once DATA is accepted, a failing or hanging QUIT is ignored, so a
  delivered message is never reported as failed.
- Errors carry the stage and numeric reply code only (`mail_unavailable` for
  network, timeouts and 4xx, retryable; `mail_rejected` for other 5xx;
  `mail_auth_failed` for 530/535 anywhere and 534/538 during AUTH). Server
  text is discarded: it echoes recipients and sometimes credentials.

**Why not `lettre`.** `lettre` 0.11 is mature and MIT-licensed. With the
features Forge would need (`smtp-transport`, `builder`, `tokio1-rustls`,
`ring`, `webpki-roots`) it would add seven packages to `Cargo.lock`:
`lettre`, `nom`, `mime`, `quoted_printable`, `email-encoding`,
`email_address` and a second `base64` (0.23 next to the workspace's 0.22);
its other dependencies (`url`, `idna`, `socket2`, `futures-util`, `httpdate`,
`fastrand`, `percent-encoding`) are already resolved through SQLx and Tokio
(checked against the crates.io manifest of 0.11.23 on 2026-10-20). It would also bring a second MIME builder whose output differs
from Forge-Go's, and a message type that would leak into Forge's API or need
a translation layer. Its TLS policy is configurable rather than fixed, so
Forge would still wrap it to keep "credentials only over TLS" and the
STARTTLS-injection check. The protocol subset above is small, parses no
hostile structured input beyond bounded reply lines, and is covered by
in-process fake-server tests (STARTTLS with a test CA, implicit TLS, name
mismatch, untrusted CA, injected bytes, stripped STARTTLS, timeouts, reply
classes). Replacement: a `lettre`-backed `Sender` remains possible behind the
same port.

### Development and tests

- `FileSender` (`FORGE_MAIL_URL=file:tmp/mail`) writes each message as a
  `0600` `.eml` file with `O_CREAT | O_EXCL` under a generated name in a
  `0700` directory, logs only the path, and warns once at start-up that mail
  is not delivered. Configuration loading and `from_config` refuse it in
  production.
- `testing::Recorder` (feature `testing`) records deep copies plus the
  encoded bytes and envelope, runs the real encoder, and simulates outages
  with `fail_with`.
- `PreviewHandler` serves registered previews (headers, HTML in a sandboxed
  iframe, text, inline images, raw source, and the exact validation error).
  Because an unset `FORGE_ENV` means development, the environment alone is
  not a safe gate: construction requires `FORGE_ENV` development or test
  **and** `FORGE_MAIL_PREVIEW=true`, which configuration loading refuses in
  production. Responses are `GET`/`HEAD` only, `nosniff`, `no-store`, and HTML
  is served under `Content-Security-Policy: default-src 'none'; ...; sandbox`.

### Templates

`Templates` renders a subject, a text part and an HTML part from askama
templates (`DynTemplate`), the same engine as the views. Data is a typed
struct; HTML templates (`.html`) escape every value, text templates (`.txt`)
escape nothing. Rendering is fully buffered: any failure is
`mail_template` and nothing is sent. A rendered subject is still validated as
a header.

### Configuration

`FORGE_MAIL_URL` (secret; `smtp://`, `smtps://`, `file:`), `FORGE_MAIL_FROM`,
`FORGE_MAIL_ALLOW_PLAINTEXT`, `FORGE_MAIL_TIMEOUT`, `FORGE_MAIL_PREVIEW`,
`FORGE_MAIL_TLS_CA_FILE` and `FORGE_AUTH_PASSWORD_RESET_URL`, with Forge-Go's
semantics: no URL parameters, ambiguous URLs refused, credentials with
control characters refused, errors never echo the URL, `FORGE_MAIL_FROM`
required with a URL and validated with the message rules, the file sender and
previews refused in production, the reset URL https (http only on
localhost) without credentials, query or fragment. An unset URL leaves mail
disabled and `from_config` returns `MailError::NotConfigured`.

### Password reset delivery

`PasswordResetEmails` composes the built-in English email (replaceable with
`with_template`) and validates its settings with a probe at start-up;
`PasswordResetMailer` implements `PasswordResetNotifier` over any `Sender`.
The token appears only in the link inside the body; failures are logged once
with the error code and SMTP stage only (never recipient, link or token) and
reported as `PasswordResetDeliveryError::Unavailable`.
`password_reset_notifier(config, app_name, telemetry)` is what generated
applications wire: the mailer when `FORGE_MAIL_URL` is set (instrumented when
telemetry is on), `UndeliverablePasswordResets` when it is not, and a
start-up error for a URL without `FORGE_AUTH_PASSWORD_RESET_URL` or
`FORGE_MAIL_FROM`. Delivery already runs on the bounded reset worker queue
(ADR 0026), off the request path, so SMTP latency reveals nothing.

### Telemetry

`Instrumented` records `forge.mail.send.duration` (label
`forge.mail.outcome`: `sent` or the error code), Forge-Go's catalogue entry,
and `send_in(parent, ...)` adds a `mail send` client span inside a traced
operation. No recipient, subject, body, header or error message is recorded.

## Consequences

- Generated full-stack PostgreSQL applications deliver reset links once the
  three variables are set and preview the reset email at `/_mail`.
- No new package enters `Cargo.lock`: the crate reuses `rustls`,
  `tokio-rustls`, `webpki-roots`, `askama`, `base64`, `getrandom`, `uuid`,
  `serde` and `tokio` (its `io-util` feature, already enabled by SQLx).
- Deviations from Forge-Go: roots are the Mozilla set (`webpki-roots`) rather
  than the operating-system store, as for the OTLP exporter; `MAIL FROM` does
  not add `BODY=8BITMIME` (the output is 7-bit); the reset link has no
  `TokenInFragment` option because the generated reset page reads the query;
  generated applications keep showing the reset pages without mail (the
  answer is identical either way) instead of hiding them; previews take a
  synchronous fixture builder; `parse_mailbox` reads quoted and plain display
  names but not encoded words or comments.
- `forge generate mailer` (typed mailers, templates, previews and tests) is
  tracked with the other generators in rocketinsidecorp/forge-rust#15.

## Not decided here

Queue-backed delivery (`forge-jobs` payloads are serde values and `Message`
is serializable, so a queue is just another `Sender`), DKIM signing, bounce
handling, provider HTTP APIs, SMTPUTF8 and IDNA.
